Progent: Securing AI Agents with Privilege Control

논문 및 이미지 출처 : https://arxiv.org/pdf/2504.11703

Abstract

AI agent 는 tool call 을 통해 external environment 와 상호작용하며, 이로 인해 unauthorized action 을 유발할 수 있는 indirect prompt injection 과 같은 attack 에 노출된다. 이러한 agent 를 안전하게 보호하는 것은 어렵다. agent 는 autonomous 하고 probabilistic 하게 동작하며, security requirement 는 user 의 task 와 execution state 에 따라 변화하고, security 와 utility 사이에는 본질적인 trade-off 가 존재한다.

본 연구에서 저자는 privilege control 을 통해 AI agent 를 보호하는 새로운 framework 인 Progent 를 제안한다. Progent 는 privilege 를 tool name 과 argument 에 대한 symbolic rule 로 구성된 security policy 로 표현한다. 이러한 rule 은 task completion 을 위해 허용되는 tool call 과 security 를 위해 차단되는 불필요한 tool call 을 지정한다. 모든 tool call 은 deterministic procedure 를 통해 이러한 policy 에 대해 검사되며, 이를 통해 principle of least privilege 를 강제한다.

다양한 user task 와 변화하는 execution context 를 처리하기 위해, LLM 은 user task 로부터 initial policy 를 자동으로 생성하고 새로운 information 이 도착함에 따라 execution 중 이를 update 한다. 제안된 각 update 는 SMT solver 에 의해 narrowing 또는 expansion 으로 판정된다. narrowing 은 자동으로 적용되고, expansion 은 explicit approval 을 요구한다. 이를 통해 agent 의 effective action space 는 approval 없이는 오직 축소될 수 있으며, 저자는 이를 monotonic confinement 라고 부른다. 이러한 deterministic update mechanism 은 adversarial input 이 존재하더라도 utility 를 유지하면서 silent privilege escalation 을 방지한다.

AgentDojo 와 ASB 에 대한 evaluation 결과, Progent 는 높은 utility 를 유지하면서 attack success rate 를 크게 감소시킨다. 또한 저자는 LangChain 및 OpenAI Agents SDK 와 같은 real-world agent framework 에서 Progent 의 effectiveness 를 보여줌으로써 practical applicability 를 추가로 검증한다.

1 Introduction

AI agent 는 general 하고 autonomous 한 task solving 을 위한 유망한 platform 으로 등장했다. 이러한 agent 의 핵심에는 large language model (LLM) 이 있으며, LLM 은 다양한 tool 집합을 통해 external environment 와 상호작용한다. 예를 들어 personal assistant agent 는 email toolkit 을 사용해 email 을 관리하고, coding agent 는 code interpreter 와 command line 을 사용한다.

Security Risks in AI Agents​

external environment 와 상호작용할 수 있는 능력은 AI agent 를 강력하게 만들며, communication, scheduling, finance 와 같은 다양한 domain 에서 task 를 수행할 수 있게 한다. 그러나 동일한 능력은 동시에 큰 attack surface 를 만든다. 최근 연구는 AI agent 에 대해 심각한 security concern 을 제기하고 있으며, attacker 는 external data source 에 adversarial instruction 을 삽입하여 agent 와 environment 의 interaction 을 악용한다.

agent 가 tool call 을 통해 이러한 data 를 retrieve 하면, 삽입된 instruction 은 agent 를 redirect 하여 unauthorized financial transaction 또는 data exfiltration 과 같은 위험한 action 을 수행하게 만들 수 있다. 이러한 유형의 attack 을 indirect prompt injection 이라고 한다.

Challenges for Securing AI Agents​

AI agent 를 보호하는 것은 여러 이유로 어렵다.

첫째, agent behavior 는 본질적으로 non-deterministic 하다. LLM 은 unstructured natural language 를 처리하며, run 마다 서로 다른 결정을 내릴 수 있다. 반면 security 는 LLM 이 어떻게 reasoning 하든, adversarial influence 하에서도 유지되는 deterministic enforcement 를 요구한다. 이 두 세계를 조화시키는 것은 쉽지 않다.

둘째, agent security 는 user task 와 agent 가 execution 동안 수집한 information 모두에 의존한다. 서로 다른 task 는 서로 다른 tool 과 argument 를 요구하며, 관련 context 는 agent 가 environment 와 상호작용함에 따라 runtime 에서 변화한다. defense 는 이러한 변화를 자동으로 추적해야 한다. 모든 security decision 에 user 를 참여시키는 것은 비현실적이며 autonomous agent 의 이점을 제거하기 때문이다.

마지막으로 agent 는 benign task 를 완료하기 위해 때때로 privilege 를 확장해야 한다. 그러나 adversary 역시 동일한 mechanism 을 악용하여 harmful action 을 유도하려 하며, legitimate expansion request 와 adversarial expansion request 모두 동일한 channel 을 통해 도착한다. security 나 utility 를 희생하지 않고 legitimate expansion 과 adversarial expansion 을 구분하는 것은 근본적인 challenge 이다. 저자는 Sec. 2 에서 running example 을 통해 이러한 challenge 를 자세히 설명한다.

Our Work: Progent​

저자는 privilege control 을 통해 AI agent 를 보호하는 새로운 framework 인 Progent 를 제안한다. 핵심 아이디어는 principle of least privilege 를 강제하는 것이다. 즉, task completion 에 필수적인 tool call 만 허용하고 불필요한 tool call 은 차단한다.

저자는 모든 external effect 가 tool call 을 통해 발생하고, agent 의 unstructured reasoning 과 달리 tool name 과 typed argument 로 이루어진 structured interface 를 제공하기 때문에 tool call 에 초점을 맞춘다. 따라서 tool call 은 deterministic security enforcement 를 수행하기에 자연스러운 지점이다.

Progent 는 tool name 과 argument 에 대한 symbolic rule 로 구성된 privilege control policy 를 사용한다. 이러한 rule 은 어떤 tool call 이 허용되고 어떤 tool call 이 차단되어야 하는지를 지정한다. 모든 tool call 은 이러한 policy 에 대해 검사되며, policy 는 해당 call 의 허용 여부를 deterministic 하게 결정한다.

context-dependent security requirement 를 처리하기 위해, Progent 는 LLM 을 사용하여 user task 로부터 initial policy 를 자동으로 생성하고 execution 동안 새로운 information 이 도착함에 따라 이를 update 한다. 이를 통해 security enforcement 는 task context 와 execution context 모두에 적응하면서 manual effort 를 최소화한다. 그러나 policy construction 에 LLM 을 도입하면 non-determinism 이 발생하며, automation 과 deterministic enforcement 사이에 근본적인 긴장이 생긴다.

이를 해결하기 위해 저자는 각 policy update 를 deterministic SMT solver 로 검사하여 narrowing 또는 expansion 으로 분류할 것을 제안한다. narrowing 은 자동으로 적용되고, expansion 은 explicit approval 을 요구한다. 따라서 agent 의 effective action space 는 approval 없이는 오직 좁아질 수 있으며, 저자는 이 특성을 monotonic confinement 라고 부른다. 그 결과 LLM 이 adversarial input 에 의해 조작되더라도 deterministic check 가 silent privilege escalation 을 방지한다. 동시에 explicitly authorized 된 경우에는 controlled privilege expansion 을 허용하여 utility 를 유지한다.

Implementation and Evaluation​

Progent 는 tool-call level 에서 동작하기 때문에 agent 와 tool 사이에 별도 module 을 삽입하여 integrate 할 수 있다. agent 내부 architecture 를 변경할 필요가 없으므로 integration 은 non-intrusive 하며 다양한 agent framework 에 generalize 할 수 있다.

저자는 AgentDojo 와 ASB 에서 Progent 를 평가한다.

  • AgentDojo 에서 Progent 는 attack success rate (ASR) 를 39.9% 에서 1.0% 로 감소시킨다.
  • ASB 에서는 ASR 를 70.3% 에서 3.9% 로 감소시킨다.
  • 두 경우 모두 agent 의 utility 를 유지한다.
  • 저자는 model choice 및 policy update approval configuration 을 포함하여 Progent 의 핵심 component 에 대한 extensive ablation study 를 수행한다.
  • 마지막으로 AgentDojo 를 MCP-based benchmark 로 확장하고 이를 LangChain 및 OpenAI Agents SDK 와 같은 다양한 real-world agent framework 에 연결하여, single-agent 및 multi-agent system 모두에서 Progent 의 effectiveness 를 보여준다.

Main Contributions​

저자의 주요 contribution 은 다음과 같다.

  • tool name 과 argument 에 대한 symbolic policy 를 사용하는 privilege control approach 를 제안하며, tool-call level 에서 deterministic enforcement 를 수행하고 SMT-based procedure 를 통해 policy update 가 expansion 인지 narrowing 인지를 판정한다.
  • user task 와 execution state 로부터 context-aware policy 를 자동으로 생성하고 update 하는 LLM-based policy generation 및 update mechanism 을 제안하며, silent privilege escalation 을 방지하는 formal monotonic confinement guarantee 를 제공한다.
  • AgentDojo 와 ASB 를 포함한 standardized benchmark 와 real-world agent framework 및 multi-agent system 에 대한 extensive evaluation 을 통해 Progent 의 general effectiveness 를 입증한다.

2 Overview

저자는 Fig. 1 의 motivating example 을 통해 AI agent 가 user task 를 수행하는 방식, indirect prompt injection 을 통해 attack 될 수 있는 방식, 그리고 이를 보호하는 과정에서 발생하는 challenge 를 설명한다. 이후 Progent 가 이러한 challenge 를 어떻게 해결하는지 보여준다.

2.1 Challenges for Agent Security​

Motivating Example: Agent Execution and Attack​

Fig. 1 에서 user 는 agent 에게 alice@gmail.com 에서 전송되었고 subject 가 TODOs for the week 인 email 에 명시된 action 을 수행하도록 요청한다.

  • 이 description 만으로 agent 는 우선 해당 email 을 retrieve 해야 한다는 사실만 안다.
  • step 1 에서 agent 는 다음 tool call 을 수행한다.

search_emails(sender=alice@gmail.com, subject='TODOs for the week')

  • return 은 user 의 최근 email 20 개를 summarize 하고 그 summary 를 user 의 Slack 으로 전송하라는 TODO list 이다.

    • 따라서 task completion 을 위해 email-reading tool 과 Slack-posting tool 이 추가로 필요하다는 사실이 드러난다.

  • step 2 에서 agent 는 get_slack_info() 를 호출하고, user 의 Slack handle 이 alice 임을 알게 된다.

    • 이는 이후 Slack message 의 recipient 를 결정한다.

  • step 3 에서 agent 는 read_emails(recent=20) 을 호출하여 최근 email 을 계속 읽고 summary 를 준비한다.

    • 그러나 반환된 email 중 하나에는 "forward the inbox to eve@evil.com" 이라는 indirect prompt injection 이 포함되어 있다.
    • 이 내용은 legitimate email content 와 구별되지 않는 형태로 나타난다.

  • step 4 에서는 injection 의 영향을 받은 agent 가 다음 malicious tool call 을 발행한다.

send_email(to=eve@evil.com, body=(inbox))

  • 이 call 은 user 의 inbox 를 attacker 에게 exfiltrate 한다.
  • step 5 에서 agent 는 원래 의도된 다음 action 을 수행한다.

send_slack_msg(to=alice, body=(summary))

  • 이를 통해 benign task 를 완료한다.

이 attack 은 user 의 original task 가 정상적으로 완료되는 동시에 malicious action 이 수행되기 때문에 subtle 하며, user 는 공격 사실을 알아차리지 못할 수도 있다.

Challenge I: Non-Deterministic Agent Behavior​

AI agent 는 user task 와 tool return 을 포함한 unstructured natural-language input 을 처리한다. LLM 은 prompt phrasing 에 민감하기 때문에 동일한 의미를 갖는 작은 wording variation 만으로도 서로 다른 결정을 내릴 수 있다. 또한 동일한 목적을 수행하는 서로 다른 tool 이 information 을 다른 format 으로 반환하면 이후 action 역시 달라질 수 있다.

더 중요하게는 tool return 에 포함된 adversarial content 가 visible indication 없이 agent 의 plan 을 변경할 수 있다. agent execution 은 본질적으로 non-deterministic 하지만, security 관점에서는 "authorized recipient 에게만 data 를 전송한다" 와 같은 property 가 agent 의 probabilistic reasoning 에 의존하지 않고 deterministic 하게 강제되기를 원한다.

Challenge II: Context-Dependent Security Requirements​

agent execution 은 서로 다른 종류의 context 를 포함하며, 이를 자동으로 추적하여 security 를 강제하는 것은 어렵다. 효과적인 defense 는 security decision 을 위해 이러한 context 를 자동으로 고려해야 한다. 모든 tool call 에 대해 user approval 을 요구하면 너무 많은 effort 가 필요하며 agent 사용의 이점을 제거한다.

저자는 agent 에 두 종류의 context 가 존재한다고 본다.

  • Task context

    • 동일한 agent 는 email summarization, flight booking, budget reconciliation 과 같은 서로 다른 task 를 처리할 수 있으며, 각 task 는 서로 다른 tool 과 tool argument 를 authorize 한다.
    • tool call 이 safe 한지는 task 에 따라 달라진다.
    • 예를 들어 send_email 은 "Alice 에게 update 를 email 로 보내라"는 task 에서는 legitimate 하지만, "unread email 을 summarize 하라"는 task 에서는 반환된 email 안의 adversarial instruction 이 agent 에게 sensitive content 를 third party 로 전송하도록 지시하여 send_email 을 data-exfiltration channel 로 만들 수 있다.
    • 모든 task 에 충분히 permissive 한 policy 는 attack 을 block 하기에 지나치게 broad 하며, 단일 task 를 위해 설계된 policy 는 다른 task 에 사용하기에는 지나치게 narrow 하다.

  • Execution context

    • AI agent 는 autonomous 하게 실행되며, runtime 에서 새로운 information 을 수집하면서 context 가 변화한다.
    • 예를 들어 step 2 이후에야 agent 는 Slack handle 이 alice 임을 알게 된다.
    • 따라서 이후 Slack message 는 alice 에게만 전송되어야 하며, 다른 사람에게 Slack message 를 전송하는 것은 block 되어야 한다.
    • 이러한 execution-gathered information 은 security-critical 하며, defense 는 이를 이용할 수 있게 되는 즉시 반영해야 한다.

Challenge III: Balancing Security and Utility​

agent 는 autonomous 하게 실행되기 때문에 새롭게 획득한 information 에 적응해야 하며, 이 과정에서 additional privilege 가 legitimately 필요할 수 있다. 그러나 동일한 channel 이 adversarial content 역시 전달할 수 있기 때문에 security 와 utility 의 균형을 맞추기 어렵다.

  • Utility 측면

    • task 를 완료하려면 agent 가 allowed tool 과 argument 집합을 dynamically 확장해야 하는 경우가 많다.
    • Fig. 1 의 example 에서 step 1 의 TODO return 은 read_emails, get_slack_info, send_slack_msg 가 추가로 필요하다는 것을 알려준다.
    • 이러한 tool 을 금지하는 defense 는 task completion 을 방해한다.

  • Security 측면

    • attacker 역시 malicious purpose 를 위해 agent 의 tool usage 를 확장하려 한다.
    • step 3 의 injection 은 external address 를 대상으로 하는 send_email 을 도입하려 한다.
    • 이를 허용하면 data exfiltration 이 가능해진다.
    • 두 request 모두 agent 의 plan 을 변경하는 tool return 이라는 동일한 channel 을 통해 도착한다.
    • 특히 injected instruction 은 agent 가 summarize 해야 하는 legitimate email content 와 동일한 tool return 안에 포함되어 있기 때문에 adversarial case 를 탐지하기 어렵다.

따라서 defense 는 task 에 legitimate 하게 필요한 경우 agent 의 allowed action 을 확장하면서도 adversarial content 로부터 발생한 expansion 은 거부해야 하며, security 나 utility 어느 쪽도 희생해서는 안 된다.

2.2 Progent: Defense via Privilege Control​

Policy-Based Security Enforcement​

Progent 는 모든 external effect 를 갖는 agent action 이 tool call 을 통해 흐르기 때문에 tool-call level 에서 동작한다. 또한 tool-call interface 는 tool name 과 typed argument 로 구성된 structured format 인 반면, agent 가 reasoning 하는 text 는 unstructured 하다. 따라서 tool call 은 자연스러운 enforcement point 이며, Progent 는 agent 의 non-deterministic behavior 에도 불구하고 security 를 deterministic 하게 강제할 수 있다.

Progent 는 agent 가 어떤 tool call 을 발행할 수 있고 어떤 tool call 이 block 되어야 하는지를 기술하는 privilege control policy 를 도입한다. policy 는 rule 의 list 로 구성된다. 각 rule 은 특정 tool 을 대상으로 하고 argument 에 대한 condition 을 지정하여 해당 tool call 의 허용 여부를 결정한다.

Fig. 1 의 example 에서 policy P4P_4P4​ 는 4 개의 allow rule 을 포함한다. 이는 tool call 의 name 이 rule 과 일치하고 argument 가 지정된 condition 을 만족하면 해당 tool call 이 허용됨을 의미한다.

  • read_emails rule 은 recent=20 인 call 만 허용한다.
  • send_slack_msg rule 은 to=alice 인 call 만 허용한다.
  • rule 은 20 과 같은 concrete value, wildcard *, regular-expression pattern 등을 사용할 수 있으므로 fine-grained constraint 를 표현할 수 있다.
  • allow rule 외에도 Progent 는 특정 pattern 과 일치하는 tool call 을 명시적으로 block 하는 forbid rule 과 여러 추가 feature 를 지원한다.

agent 가 tool call 을 발행하면 Progent 는 이를 current policy 의 rule 과 match 하고 deterministic 하게 allow 또는 block 한다. 어떤 rule 과도 match 하지 않는 call 은 default 로 block 된다.

  • step 4 에서 P4P_4P4​ 에는 send_email 에 대한 allow rule 이 없다.

    • 따라서 Progent 는 malicious call send_email(to=eve@evil.com, body=(inbox)) 을 deterministic 하게 block 한다.
    • 이후 agent 가 user task 를 조정하여 계속 수행할 수 있도록 denial 의 이유를 설명하는 fallback error 를 반환한다.

  • step 5 에서는 P5=P4P_5=P_4P5​=P4​ 를 기준으로 check 한다.

    • benign call send_slack_msg(to=alice, body=(summary)) 는 P5P_5P5​ 의 Slack rule 과 match 하므로 allow 된다.
    • 따라서 task 가 완료된다.

이 check 는 structured policy rule 에 대한 purely symbolic operation 이므로 모든 security decision 이 deterministic 하며, Challenge I 을 직접 해결한다.

LLM-Based Policy Construction and Update​

agent security 는 context 에 의존하므로 Progent 는 새로운 information 이 도착함에 따라 변화하는 per-step policy 를 유지한다. step iii 에서 gating privilege control policy 는 PiP_iPi​ 이며, 해당 step 에서 agent 가 발행할 수 있는 tool call 을 정확하게 열거한다.

initial policy P1P_1P1​ 은 user task 로부터 도출된다. running example 에서 P1P_1P1​ 은 특정 sender 와 subject 를 갖는 search_emails 만 허용한다.

LLM-based updater 는 task context 와 execution context 모두에 대해 reasoning 하여 policy management 를 자동화한다. 그렇지 않으면 모든 가능한 user request 에 대해 per-step rule 을 manual 하게 작성해야 한다.

i>1i>1i>1 인 경우 updater 는 step i−1i-1i−1 의 tool return 과 이전 policy Pi−1P_{i-1}Pi−1​ 을 기반으로 새로운 policy PiP_iPi​ 를 제안한다.

  • step 1 이후 반환된 TODO 는 추가 tool 이 필요함을 드러낸다.

    • updater 는 read_emails, get_slack_info, send_slack_msg 에 대한 allow entry 를 추가한 P2P_2P2​ 를 제안한다.

  • step 2 이후 alice 라는 handle 이 알려진다.

    • updater 는 Slack entry 를 send_slack_msg(to=alice, body=*) 로 좁힌 P3P_3P3​ 를 제안한다.

  • step 3 이후 반환된 email 에는 send_email 을 도입하려는 injection 이 포함되어 있다.

    • 그러나 policy 는 변경되지 않으며 P4=P3P_4=P_3P4​=P3​ 이다.

Deterministic Control of Policy Expansion and Narrowing​

policy update 는 allowed tool call 집합을 expand 하거나 narrow 할 수 있다. narrowing 은 permission 만 제거하므로 safe 하다. 반면 expansion 은 sensitive 하다. P1→P2P_1 \rightarrow P_2P1​→P2​ 처럼 utility 를 위해 필요할 수도 있지만, step 3 의 injection 처럼 attack 에 의해 발생할 수도 있다.

Progent 는 narrowing 과 expansion 을 다르게 처리하기 위해 모든 proposed update 를 적용하기 전에 판정한다.

PPP 에서 P′P'P′ 으로의 update 에 대해:

  • P′P'P′ 이 허용하는 tool call 집합이 PPP 보다 strictly larger 하면 expansion 으로 정의한다.
  • 반대로 P′P'P′ 이 허용하는 모든 call 을 PPP 역시 허용한다면 narrowing 으로 판정한다.
  • P′=PP'=PP′=P 인 경우 역시 narrowing 에 포함한다.

Progent policy 는 symbolic 하기 때문에 두 relation 모두 SMT solver 로 decidable 하며, 따라서 완전히 deterministic 한 judgment 가 가능하다.

narrowing update 는 자동으로 적용된다. expansion 은 적용되기 전에 explicit approval 을 요구한다. Progent 는 모든 expansion 을 자동으로 deny 하거나, human review 로 routing 하거나, 모두 자동으로 approve 하는 등의 configurable approver setting 을 지원한다.

Fig. 1 의 example 에서는 다음과 같다.

  • P1→P2P_1 \rightarrow P_2P1​→P2​

    • read_emails, get_slack_info, send_slack_msg 를 추가하므로 expansion 이다.
    • SMT solver 가 이를 detect 하고 approval 이후에만 P2P_2P2​ 가 적용된다.

  • P2→P3P_2 \rightarrow P_3P2​→P3​

    • Slack recipient 를 alice 로 bind 하므로 P3⊂P2P_3 \subset P_2P3​⊂P2​ 인 narrowing 이다.
    • SMT solver 가 이를 detect 하고 P3P_3P3​ 를 자동으로 적용한다.

  • P3→P4P_3 \rightarrow P_4P3​→P4​

    • step 3 의 injection 에 대해 두 가지 상황이 가능하다.
    • updater 가 safety alignment 등을 통해 injection 을 인식하면 expansion 을 제안하지 않으며 P4=P3P_4=P_3P4​=P3​ 가 자동으로 적용된다.
    • updater 가 속아서 send_email 을 추가하도록 제안하더라도 SMT solver 가 expansion 을 detect 하며 approver 가 이를 deny 할 수 있다.
    • 어느 경우든 P4=P3P_4=P_3P4​=P3​ 이며 step 4 의 malicious call 은 block 된다.

따라서 LLM 이 manipulate 되거나 hallucinate 하더라도 deterministic judgment 때문에 explicit approval 없이 새로운 permission 이 부여될 수 없다. 동시에 utility-driven expansion 은 approval 을 통해 허용될 수 있다.

AgentDojo experiment 에서 approval 이 필요했던 update 는 전체의 6% 에 불과했다. 따라서 human user 가 참여하더라도 approval cost 는 낮다.

Progent’s Security Guarantee​

deterministic policy enforcement 와 deterministic expansion control 을 결합하면 agent 의 effective action space 는 explicit approval 없이 오직 좁아질 수 있다. 저자는 이 property 를 monotonic confinement 라고 부른다.

이는 attack 이 agent privilege 를 silent 하게 escalate 할 수 없음을 guarantee 한다. expansion request 만 approval 을 요구하고, 그 외 모든 security decision 은 deterministic 하게 처리된다.

추가로 Progent 는 모든 task 에 걸쳐 persistent constraint 를 적용하는 generic policy 와 expansion request 처리 방식을 제어하는 configurable approver module 을 지원한다.

3 Problem Statement and Threat Model

이 Sec. 에서 저자는 먼저 AI agent 를 정의하고, 이를 이후 Progent 설명의 기반으로 사용한다. 이후 threat model 을 제시한다.

3.1 AI Agents​

저자는 task solving 에 AI agent 를 사용하는 general setup 을 고려하며, 이는 네 주체로 구성된다.

action 은 tool call 일 수도 있고 completion signal 일 수도 있다.

3.2 Threat Model​

Attacker Goal​

attacker 의 goal 은 agent 의 task-solving flow 를 방해하여 attacker 에게 어떤 방식으로든 이익이 되는 unauthorized action 을 수행하도록 만드는 것이다.

agent 는 external environment 와 tool call 을 통해 상호작용하므로 이러한 dangerous behavior 는 malicious tool call 로 나타난다. tool call 로부터 가능한 outcome 이 매우 다양하기 때문에 attacker 는 다양한 downstream damage 를 유발할 수 있다. 예를 들어 dangerous data erasure operation 이나 unauthorized financial transaction 을 유도할 수 있다.

Attacker Capabilities​

저자의 threat model 은 attacker capability 에 practical constraint 를 둔다.

저자는 attacker 가 environment EEE 의 agent external data source, e.g., email, 를 manipulate 하여 malicious command 를 삽입할 수 있다고 가정한다. agent 가 tool call 을 통해 이러한 data 를 retrieve 하면 injected command 가 agent behavior 를 변경할 수 있다.

그러나 user UUU 는 benign 하다고 가정하므로 user input query 는 항상 benign 하다. 즉, user query o0o_0o0​ 는 benign 하고, i>0i>0i>0 에 대한 observation oio_ioi​ 는 attacker 가 control 할 수 있다고 가정한다.

반면 attacker 는 model 변경이나 system prompt 변경과 같은 agent internal component 를 modify 할 수 없다. real-world 에서 agent 는 일반적으로 external party 에게 black-box 로 제공되기 때문이다.

Progent’s Defense Scope​

Progent 의 goal 은 AI agent 의 tool call 에 대해 privilege control policy 를 enforce 하는 general framework 를 제공하는 것이다. evaluation 이 보여주듯 Progent 는 다양한 scenario 에서 agent protection 에 효과적으로 활용될 수 있다.

그러나 몇 가지 attack 은 처리할 수 없으며, 이들은 본 연구의 scope 밖에 있다.

  • 첫째, Progent 는 user task 수행에 필요한 least privilege 내부에서 이루어지는 attack 을 방어할 수 없다.

    • 예를 들어 attacker 가 valid option 가운데 attacker product 를 선호하도록 agent 를 속이는 preference manipulation attack 이 이에 해당한다.

  • 둘째, Progent 는 tool call 을 constrain 하는 데 초점을 맞추기 때문에 text output 자체를 대상으로 하는 attack 은 처리하지 않는다.

4 Progent’s Privilege Control Policy

이 Sec. 에서는 Progent 의 privilege control policy 를 소개한다. policy definition, runtime enforcement, 그리고 SMT solving 을 이용하여 두 policy 를 비교하고 하나가 다른 하나의 expansion 인지 narrowing 인지 판단하는 방법을 설명한다.

4.1 Policy Definition​

Progent 의 privilege control policy 는 expressive 하고 강력한 privilege control 방법을 제공한다.

Progent policy PPP 는 agent 가 발행할 수 있는 tool call 집합을 collectively 설명하는 rule list 이다. 각 rule R∈PR \in PR∈P 는 특정 tool 을 대상으로 하며 argument 를 기반으로 tool call 을 allow 또는 forbid 하기 위한 condition 을 지정한다. 또한 rule 의 Fallback operation 은 blocked tool call 을 처리하는 방식을 설명할 수 있다.

  • Effect EEE 는 rule 이 tool call 을 allow 할지 forbid 할지를 지정한다.
  • ttt 는 target tool identifier 이다.
  • 이후 eie_iei​ 는 tool argument 를 기반으로 tool call 을 allow 또는 block 할 시점을 지정하는 condition 의 conjunction 을 정의한다.

이러한 condition 은 tool call 의 safety 가 특정 argument 에 의존하는 경우가 많기 때문에 중요하다.

각 condition eie_iei​ 는 tool 의 iii 번째 argument 인 pip_ipi​ 에 대한 boolean expression 이다. 다음과 같은 다양한 operation 을 지원한다.

Fallback Action​

각 rule 은 tool call 이 disallowed 되었을 때 실행되는 fallback function fff 를 포함한다. fff 의 주요 목적은 alternative course of action 을 guide 하는 것으로, agent 에 어떻게 진행해야 하는지 feedback 을 제공하거나 human 을 final decision 에 참여시킬 수 있다.

현재 저자는 세 종류의 fallback function 을 지원하며, 향후 additional type 을 추가할 수 있다.

  • agent execution 을 즉시 terminate 한다.
  • user 에게 notify 하고 user 가 다음 step 을 결정하도록 한다.
  • tool call 을 execute 하는 대신 error message msg 를 result 로 반환한다.

본 논문에서는 default 로 세 번째 option 을 사용하며, 다음과 같은 feedback message 를 agent 에 제공한다.

The tool call is not allowed due to {reason}. Please try other tools or arguments and continue to finish the user task: {o0}.

{reason} field 는 rule 에 따라 달라지며, 제공된 argument 가 rule condition 을 어떻게 violate 하는지 등을 설명한다.

이는 automated feedback mechanism 으로 작동하여 agent 가 strategy 를 조정하고 original user task 를 계속 수행하도록 한다. 예를 들어 Fig. 1 의 running example 에서 step 4 의 send_email 이 block 된 후 fallback message 를 통해 agent 는 step 5 에서 benign task 를 계속 수행하여 성공적으로 완료할 수 있다.

5 Securing Agent Execution with Progent

Sec. 4 의 policy enforcement 를 기반으로, 저자는 Progent 가 full agent execution 을 어떻게 보호하는지와 LLM 을 통해 policy 를 자동으로 generate 및 update 하는 방법을 설명한다.

Agent Execution Loop with Progent​

Progent 는 standard agent execution loop 에 additional module 을 삽입한다.

execution 시작 시 policy PPP 는 user task 를 기반으로 initialize 된다. user query 가 benign 하다는 저자의 threat model 아래에서 initialized PPP 는 principle of least privilege 에 따라 tool usage 와 argument 를 정확하게 identify 하고 restrict 할 것으로 기대된다.

agent 가 tool call cic_ici​ 를 발행하면 unprotected tool call cic_ici​ 자체를 실행하는 대신 policy-governed version P(ci)P(c_i)P(ci​) 를 실행한다.

initial policy 는 trusted context 에 기반하지만, agent 는 execution 동안 새로운 contextual information 을 dynamically 수집한다. 이러한 evolving context 때문에 external information 을 반영하여 현재 least-privilege requirement 를 유지하도록 policy 를 update 해야 한다.

그러나 runtime environment 에서 얻은 contextual information 은 항상 trustworthy 하다고 볼 수 없기 때문에 policy update 는 추가적인 complexity 를 도입한다. potentially untrusted context 를 기반으로 policy 를 update 할 때 새로운 attack surface 가 생기지 않도록 신중한 design 이 필요하다.

이를 위해 policy update 는 두 단계로 수행된다.

  • 먼저 candidate updated policy P′P'P′ 을 생성한다.

  • 다음으로 Sec. 4.3 의 SMT solver 를 사용하여 A(P′)⊆A(P)A(P') \subseteq A(P)A(P′)⊆A(P) 인지 확인한다.

    • 그렇다면 update 는 narrowing 이며 자동으로 accept 된다.
    • 그렇지 않으면 expansion 이므로 approval 을 요구한다.

이 deterministic check 는 approval 없이 policy update 가 privilege 를 오직 narrow 할 수 있게 하고, 모든 expansion 은 explicit approval 을 요구하도록 한다.

expansion request 처리 방식은 approver module 을 통해 configure 할 수 있으며, 다음을 지원한다.

  • automatic denial
  • automatic approval
  • per-tool approval rule
  • human review

Fig. 1 의 running example 에서 P2P_2P2​ 에서 P3P_3P3​ 로의 update 는 narrowing 이므로 자동으로 적용되고, P1P_1P1​ 에서 P2P_2P2​ 로의 update 는 expansion 이므로 approval 을 요구한다.

agent security 는 task context 와 execution context 모두에 의존하므로 가능한 모든 user task 에 대해 per-step policy 를 manual 하게 작성하는 것은 비현실적이다. 이를 해결하기 위해 저자는 LLM 을 사용하여 이러한 context 를 reasoning 하고 policy 를 자동으로 generate 및 update 한다.

Initial Policy Generation​

initial policy PPP 는 available tool 집합 TTT 와 initial user query o0o_0o0​ 를 포함하는 context 를 기반으로 LLM 이 생성한다.

LLM 은 user query 에 표현된 task requirement 를 해석하고 task-specific policy 를 생성한다. 저자의 threat model 에서는 user query 가 benign 하므로 이 단계에서 LLM 은 trusted content 만 본다.

Sec. 8.2 에서 저자는 initial LLM-generated policy 만으로도 후속 update 없이 많은 indirect prompt injection attack 을 효과적으로 방어할 수 있음을 experimentally 보여준다.

구체적으로 ASR 를 39.9% 에서 2.5% 로 감소시키면서 utility 를 유지한다. 이러한 effectiveness 는 model 이 tool call 을 plan 하고 least-privilege policy 를 생성할 수 있는 능력과 일치한다.

Policy Update​

initial policy 는 이미 강한 defense 를 제공하지만, dynamic agent planning 때문에 external information 을 포함하여 utility 와 security 를 모두 유지하기 위한 policy update 가 필요하다.

policy initialization 과 달리 policy update 는 environment 로부터의 content 를 포함해야 하며, 이러한 content 는 untrusted 하고 attacker 에 의해 manipulate 될 수 있다.

adversarial input 에 대응하기 위해 candidate generation 은 두 sub-step 으로 분리된다.

  • 첫 번째 sub-step 에서 LLM 은 policy update 가 potentially 필요한지를 판단한다.

    • input 으로 available tool TTT, initial user query o0o_0o0​, current tool call cic_ici​ 를 받는다.
    • 중요한 점은 tool call result oio_ioi​ 가 이 단계에서는 제외된다는 것이다.
    • 따라서 update 여부를 결정하는 decision 은 potentially malicious content 에 노출되지 않은 상태에서 이루어진다.
    • tool call 이 non-informative 하거나 irrelevant 한 action, e.g., irrelevant file 읽기, file 쓰기, email 전송, 에 해당하면 update 가 필요하지 않다.

  • LLM 이 update 가 필요하다고 판단하면 두 번째 sub-step 에서 candidate policy P′P'P′ 을 생성한다.

    • 이때 TTT, o0o_0o0​, cic_ici​, tool call result oio_ioi​, current policy PPP 를 포함한 full available context 를 사용한다.

생성된 P′P'P′ 은 SMT-based comparison 으로 narrowing 인지 expansion 인지 판정되어 그에 따라 처리된다.

LLM-generated candidate P′P'P′ 가 environment 의 adversarial content 에 영향을 받더라도 SMT-based comparison 은 malicious expansion 을 detect 하여 silent 하게 적용되는 것을 방지한다.

6 Progent’s Security Guarantee

저자는 Progent 가 제공하는 security guarantee 를 제시한다.

SMT-based expansion check 는 자동으로 적용되는 모든 policy update 가 다음을 만족하도록 한다.

A(P′)⊆A(P)(5)A(P') \subseteq A(P) \tag{5}A(P′)⊆A(P)(5)

여기서 A(P)A(P)A(P) 는 Sec. 4.3 에서 정의한 agent 의 allowed tool call 집합이다.

Eq. (5) 가 모든 update step 에서 모든 tool 에 대해 강제되므로 approved expansion 사이에서 allowed tool call 집합은 monotonically decreasing sequence 를 형성한다.

A(P(0))⊇A(P(1))⊇A(P(2))⊇⋯(6)A(P^{(0)}) \supseteq A(P^{(1)}) \supseteq A(P^{(2)}) \supseteq \cdots \tag{6}A(P(0))⊇A(P(1))⊇A(P(2))⊇⋯(6)

저자는 이 property 를 Monotonic Confinement 라고 부른다. 즉, explicit approval 없이 agent 의 action space 는 증가할 수 없다.

Fig. 1 의 running example 에서 P1P_1P1​ 에서 P2P_2P2​ 로의 update 는 approval 을 요구하는 expansion 이다. 이 approval 이후 invariant 는 다음 sequence 가 오직 narrow 되도록 guarantee 한다.

A(P_2) \supseteq A(P_3) ======================= # A(P_4) A(P_5)

따라서 approval 사이에서 agent permission 은 오직 감소할 수 있다.

7 Implementation

Progent’s Privilege Control Policy​

저자는 Progent policy 를 JSON Schema 로 구현한다. state-of-the-art LLM service provider 가 JSON 을 사용해 tool call 을 format 하기 때문에 JSON Schema 는 tool call 을 policy rule 과 비교하여 validate 하는 자연스러운 선택이다.

JSON 은 LLM training data 에 널리 포함되어 있으므로 LLM 은 fine-tuning 없이 syntactically correct 한 JSON-format policy 를 생성할 수 있으며, 이를 통해 Sec. 5 의 automated policy generation 및 update pipeline 이 가능해진다.

저자는 policy enforcement 에 jsonschema library 를 사용하고, Sec. 4.3 의 policy comparison 구현에는 Z3 SMT solver 를 사용한다.

Modular Integration​

Progent 는 modular design 덕분에 agent 와 tool 사이에 policy check 를 삽입하는 방식으로 integrate 할 수 있으며 agent 내부 architecture 를 변경할 필요가 없다.

저자는 두 가지 complementary integration mode 를 제공한다.

  • Library mode

    • developer 가 최소한의 code change 로 Progent 를 agent runtime 에 직접 embed 한다.

  • Proxy mode

    • end user 가 agent code 를 변경하지 않고 endpoint 를 Progent proxy server 로 redirect 하여 agent 를 transparently 보호한다.

real-world agent framework 와의 concrete integration example 은 Sec. 8.3 에서 설명한다.

Generic Policies​

많은 deployment scenario 에서는 서로 다른 stakeholder 가 모든 user task 에 걸쳐 유지되어야 하는 persistent security requirement 를 가진다.

예를 들어:

  • organization 은 data-governance rule 을 요구할 수 있다.
  • agent developer 는 sensitive tool 에 대한 access 를 restrict 할 수 있다.
  • end user 는 personal data 를 보호하려 할 수 있다.

Progent 는 execution 내내 fixed 상태로 유지되는 manually specified generic policy 를 통해 이를 지원한다.

generic policy 와 task-specific policy 는 sequential 하게 적용된다.

  • generic policy 를 먼저 evaluate 한다.
  • generic policy 가 call 을 명시적으로 allow 하거나 forbid 하지 않으면 task-specific policy PPP 를 적용한다.
  • 그렇지 않으면 generic policy 의 decision 을 따른다.

이를 통해 generic policy 가 forbid 한 tool call 은 즉시 block 되며 PPP 로 override 할 수 없다.

따라서 다음 Generic Confinement 를 보장한다.

A(Pgeneric,P)⊆A(Pgeneric)A(P_{\text{generic}}, P) \subseteq A(P_{\text{generic}})A(Pgeneric​,P)⊆A(Pgeneric​)

여러 stakeholder 가 서로 다른 authority level 을 가진 각자의 generic policy 를 제공하는 경우 Progent 는 explicit priority ordering 을 갖는 multiple generic-policy layer 를 지원한다.

generic policy PA,PB,PC,PDP_A, P_B, P_C, P_DPA​,PB​,PC​,PD​ 가 priority 순으로 주어지면 다음과 같이 적용된다.

(((PA,PB),PC),PD)(c)(((P_A,P_B),P_C),P_D)(c)(((PA​,PB​),PC​),PD​)(c)

여기서 PAP_APA​ 가 가장 높은 priority 를 가진다.

higher-priority policy 는 먼저 enforce 되며 lower-priority policy 로 override 될 수 없다. 반면 lower-priority policy 는 remaining action space 를 추가로 restrict 할 수 있다. 따라서 lower-priority policy 나 task-specific policy 가 stronger generic guarantee 를 약화시킬 수 없다.

Approver Module​

SMT-based expansion check 가 proposed update 가 policy 를 expand 한다고 detect 하면, default 로 해당 update 가 적용되기 전에 confirmation 을 요구한다.

Progent 는 expansion request 처리 방식을 제어하는 configurable approver module 을 포함한다.

  • 가장 coarse 한 level 에서는 desired security-utility trade-off 에 따라 모든 expansion 을 automatically approve 하거나 automatically deny 할 수 있다.
  • 보다 fine-grained 한 level 에서는 특정 trusted context, e.g., trusted local data 만 access 하는 tool, 에 대해 expansion 을 auto-approve 하면서 다른 tool 에 대해서는 confirmation 을 요구하는 per-tool approval rule 을 정의할 수 있다.
  • approver module 은 initial policy 와 모든 expansion request 에 대해 human review 를 요구하도록 configure 할 수도 있으며, 이는 security-critical deployment 에 additional assurance 를 제공한다.

8 Experimental Evaluation

이 Sec. 에서는 Progent 에 대한 comprehensive evaluation 을 제시한다. 먼저 두 popular benchmark 에서 general effectiveness 를 평가하고, 이후 여러 component 의 impact 를 분석하며, 마지막으로 real-world agent 및 multi-agent system 에서 평가한다.

8.1 Progent’s General Effectiveness​

Evaluation Setup​

저자는 두 popular benchmark 에서 Progent 를 평가한다.

첫 번째는 state-of-the-art prompt injection benchmark 인 AgentDojo 이다. AgentDojo 는 일상생활에서 흔한 네 종류의 agent use case 를 포함한다.

  • Banking: banking-related operation 수행
  • Slack: Slack message 처리, web page 및 file 읽기
  • Travel: flight, restaurant, car rental 탐색 및 reservation
  • Workspace: email, calendar, cloud drive 관리

attacker 는 environment 에 malicious prompt 를 inject 하고, 이 prompt 는 tool call 을 통해 agent workflow 로 반환되어 agent 에게 attack task 를 실행하도록 지시한다.

두 번째는 ASB benchmark 이다. ASB 역시 AgentDojo 와 유사하게 environment 를 통한 indirect prompt injection 을 고려하며 10 개의 agent scenario 와 5 개의 attack template 을 제공한다.

저자는 defense 의 두 가지 핵심 aspect 를 평가한다.

  • Utility: benign user task completion success rate

    • no-attack setting
    • under-attack setting

  • Security: attack success rate (ASR)

agent 의 underlying LLM 과 policy generation 및 update 를 위한 LLM 모두에 일관되게 gpt-4o 를 사용한다.

expansion approval 에 대해서는 user 가 모든 policy-expansion request 를 항상 accept 하도록 approver 를 configure 했다고 가정한다. 이는 security awareness 가 제한적이고 실제로 risky decision 을 내릴 수 있는 user 를 simulate 하는 worst-case scenario 이다.

AgentDojo​

AgentDojo 의 다양한 4 개 agent category 에 Progent 를 적용하기 위해 저자는 generic privilege control policy 와 LLM-generated 및 dynamically updated task-specific policy 를 결합한다.

generic policy 에서는 agent 가 task planning 을 위해 information 을 수집할 때 흔히 사용하는 non-sensitive, read-only tool 을 globally allow 한다.

저자는 이 setting 에서 어떤 tool 또는 tool-call argument 도 manual 하게 forbid 하지 않는다. 대신 automated pipeline 이 corresponding policy 를 generate 및 update 하도록 한다.

이 setup 은 다음 조건을 갖는 worst-case scenario 를 나타낸다.

  • user 는 trusted argument list 를 정의하지 않는다.
  • sensitive tool 을 generic policy 에서 restrict 하지 않는다.
  • 모든 policy expansion request 를 approve 한다.
  • 따라서 limited security awareness 를 가진 user 가 risky decision 을 내리는 상황을 simulate 한다.

저자는 Progent 를 여러 prior defense 와 비교한다.

  • repeat_user_prompt

    • 각 tool call 뒤에 user query 를 반복한다.

  • spotlighting_with_delimiting

    • 모든 tool call result 를 special delimiter 로 format 하고, agent 에 delimiter 내부 instruction 을 무시하도록 prompt 한다.

  • tool_filter

    • agent execution 전에 user task solving 에 필요한 tool 집합을 LLM 이 제시하도록 prompt 하고, 나머지 tool 을 available toolset 에서 제거한다.

  • transformers_pi_detector

    • fine-tuned DeBERTa classifier 를 사용하여 각 tool call result 의 prompt injection 을 detect 하고, injection 탐지 시 agent 를 abort 한다.

  • DataSentinel

    • game-theoretically fine-tuned detector 이다.

  • LlamaPromptGuard2

    • Llama team 이 제공하는 prompt injection detector 이다.

Fig. 3 의 결과는 다음과 같다.

  • no-defense baseline 의 ASR 는 39.9% 이다.

  • Progent 는 이를 1.0% 로 크게 감소시킨다.

  • 동시에 no-attack 및 under-attack scenario 모두에서 utility 를 유지한다.

  • 이는 Progent 가 principle of least privilege 를 성공적으로 enforce 하여 user task completion 에 필요한 tool call 을 허용하면서 malicious tool call 을 block 함을 의미한다.

  • tool_filter 는 tool argument 를 무시하는 coarse-grained approach 때문에 더 큰 utility 감소와 높은 ASR 를 보인다.

    • entire tool 을 block 하면 utility 가 손상된다.
    • entire tool 을 allow 하면 attack 이 성공할 수 있다.

  • 세 prompt injection detector 인 transformers_pi_detector, DataSentinel, LlamaPromptGuard2 역시 ineffective 하다.

    • training distribution 과 유사한 dataset 에서는 잘 작동할 수 있지만 AgentDojo 로 generalize 하지 못하며 false positive 와 false negative 가 높게 나타난다.

ASB​

AgentDojo 와 유사하게 저자는 ASB 에서도 LLM-based policy generation 을 이용한 autonomous approach 를 사용한다. Sec. 5 의 방법을 사용하지만 worst-case scenario 를 simulate 하기 위해 manually defined generic policy 를 제공하지 않는다.

저자는 다음 prior defense 와 비교한다.

  • delimiters_defense

    • user query 를 delimiter 로 감싸고 delimiter 내부 user query 만 실행하도록 agent 를 prompt 한다.

  • ob_sandwich_defense

    • tool call result 마지막에 user task 를 포함한 additional instruction prompt 를 append 한다.

  • instructional_prevention

    • user query 를 reconstruct 하고 user task 를 제외한 모든 command 를 disregard 하도록 agent 에 요청한다.

Fig. 4 의 결과는 다음과 같다.

  • Progent 는 no-defense setting 과 comparable 한 utility 를 유지한다.

    • policy 가 benign user task completion 에 필요한 normal functionality 를 block 하지 않기 때문이다.
    • LLM-generated policy 는 user task 에 필요한 tool 을 성공적으로 identify 하고 이를 allow 한다.

  • Progent 는 ASR 를 70.3% 에서 3.9% 로 크게 감소시킨다.

  • 저자는 LLM-generated policy 의 failure case 를 추가로 조사한다.

    • 대부분의 failure 는 attack tool call 의 name 과 description 이 benign tool 과 매우 유사하고 user task 와 밀접하게 관련되어 있기 때문에 발생한다.
    • 따라서 어떤 tool call 이 trusted 한지에 대한 prior knowledge 가 없다면 human 에게도 이러한 attack tool call 을 identify 하기 어렵다고 저자는 판단한다.

  • 추가적인 human insight 를 반영한 manual rule 을 Progent policy 로 표현하면 ASR 를 provably 0% 로 줄일 수 있다.

  • prior defense 는 ASR 감소에 ineffective 하다.

8.2 Ablation Studies​

Different Approver Configurations​

Sec. 7 에서 설명한 것처럼 Progent 의 approver module 은 policy expansion 처리 방식을 control 한다.

저자는 automation 과 security 사이의 trade-off 를 systematic 하게 분석하기 위해 4 가지 representative configuration 을 비교한다. 처음 3 개는 fully automatic 이고 마지막 하나는 human review 를 포함한다.

  • Disable Update

    • LLM 이 initial policy 를 생성하고 자동으로 accept 한다.
    • policy update mechanism 을 disable 한다.
    • 따라서 initial policy 가 execution 동안 fixed 상태로 유지된다.

  • Auto-Deny

    • LLM 이 benign user query 로부터 initial policy 를 생성하고 자동으로 accept 한다.
    • execution 동안 모든 narrowing update 는 적용하지만 모든 expansion update 는 deny 한다.

  • Auto-Approve

    • LLM 이 benign user query 로부터 initial policy 를 생성하고 자동으로 accept 한다.
    • execution 동안 narrowing 과 expansion 을 포함한 모든 update 를 자동으로 accept 한다.

  • Manual Approval

    • human 이 initial policy 와 execution 중 모든 expansion update 를 review 한다.
    • inappropriate rule 은 policy 에서 제거한다.

Auto-Approve 는 모든 expansion 을 review 없이 accept 하는 worst-case scenario 이므로, 저자는 다른 experiment 에서 이를 default configuration 으로 사용한다.

반면 Auto-Deny 는 모든 expansion 을 reject 하여 security 와 automation 사이의 conservative balance 를 제공한다.

Disable Update 는 initialization 이후 policy 를 fixed 하게 유지하므로 deterministic stability 를 제공하지만 dynamic context 에 대한 adaptability 를 감소시킬 수 있다.

Manual Approval 은 모든 policy 를 user 가 explicit 하게 review 하기 때문에 가장 강한 security 를 제공하지만 manual effort 가 요구되며 security-critical environment 에 더 적합하다.

Fig. 5 의 결과는 다음과 같다.

  • Disable Update

    • no-defense baseline 과 비교하면 ASR 를 효과적으로 감소시킨다.
    • 많은 task 의 goal 이 user query 에 명확하게 정의되어 있으므로 initial context 만으로 생성한 policy 가 이미 강한 security protection 을 제공하기 때문이다.

  • Auto-Deny

    • fully automated configuration 가운데 가장 높은 security level 을 달성한다.
    • 모든 update 가 invariant check 에 의해 strict 하게 bounded 되기 때문이다.

  • Auto-Approve

    • policy 가 initial invariant 를 넘어 expand 하는 것을 허용한다.
    • Disable Update 와 비교해 utility 와 security 모두 개선된다.
    • 그러나 widened policy 가 malicious action 을 의도치 않게 permit 할 수 있으므로 ASR 는 Auto-Deny 보다 약간 높다.
    • 이 때문에 실제 사용에서는 expansion 에 explicit approval 이 요구된다.

  • Manual Approval

    • human review 를 통해 ASR 를 0% 로 감소시킨다.
    • 이는 human oversight 가 automatic pipeline 이 놓칠 수 있는 complex security requirement 를 포착할 수 있음을 보여준다.

이 결과는 defense automation 과 security guarantee 사이의 trade-off 를 보여주며, Progent 가 automated approver configuration 과 manual approver configuration 을 모두 지원한다는 장점을 보여준다.

또한 SMT-based expansion check 이후 approval 이 필요한 expansion 은 전체 policy update 의 6% 뿐이었다. 나머지는 자동으로 처리되는 narrowing 이다. 따라서 Progent 는 approval overhead 를 낮게 유지하면서 strong security 를 제공할 수 있다.

Different Model Choices​

먼저 저자는 automated policy generation 및 update 에 사용하는 model choice 를 탐색한다. underlying agent LLM 을 gpt-4o 로 고정하고 서로 다른 policy LLM 으로 AgentDojo agent 를 실행한다.

Fig. 6 의 결과는 다음과 같다.

  • Progent 는 다양한 LLM 을 policy generation 및 update 에 사용했을 때 모두 effective 하다.
  • 모든 model 에서 ASR 를 5% 미만으로 감소시킨다.
  • 가장 성능이 좋은 LLM 에서는 ASR 가 1% 이다.

다음으로 policy LLM 을 gpt-4o 로 고정하고 여러 underlying agent LLM 을 사용한다. 저자는 no-defense baseline 과 gpt-4o 를 사용하여 policy 를 generate 및 update 하는 Progent 를 비교한다.

Fig. 7 의 결과는 다음과 같다.

  • Progent 는 서로 다른 agent LLM 전반에서 effective 하다.

  • no-attack 상황에서 utility 를 유지하거나 marginal reduction 만 발생시킨다.

  • attack 상황에서는 utility 를 향상시키고 여러 model 에서 ASR 를 크게 감소시킨다.

  • claude-sonnet-4 와 Meta-SecAlign-70B 는 자체적으로 이미 강한 safety mechanism 을 갖고 있다.

    • defense 없이 각각 ASR 6.8%, 4.8% 를 달성한다.
    • Progent 적용 후 각각 0.5%, 0.3% 까지 추가로 감소한다.
    • 이는 약 90% 의 attack 을 추가로 방어하는 것이다.

따라서 Progent 는 existing defense mechanism 을 complement 하며 practical 한 defense-in-depth layer 로 동작한다.

8.3 Real-World Agents Integration​

real-world agent 와 multi-agent system 을 평가하기 위해 저자는 먼저 MCP-based benchmark 를 구축한다. 이후 Progent 를 real-world agent 및 multi-agent system 에 integrate 하여 realistic deployment scenario 에서 performance 와 practicality 를 평가한다.

저자는 다음 real-world agent development framework 및 agent product 를 평가한다.

  • LangChain
  • OpenAI Agents SDK
  • OpenHands
  • AutoGen

MCP-Based Benchmark​

Sec. 8 의 benchmark 는 각각 자체 agent implementation 을 사용한다. Progent 의 practicality 와 effectiveness 를 보다 complex 한 real-world setting 에서 보여주기 위해 저자는 이를 popular agent development framework 및 product 에 integrate 한다.

real-world agent 를 평가하려면 safe interaction 과 realistic attack simulation 을 위한 sandboxed environment 가 필요하다.

이를 위해 저자는 AgentDojo environment 와 tool 을 MCP server 로 migrate 하고, 모든 benign task 와 attack task 를 함께 포함하여 real-world agent 와 직접 interface 할 수 있는 새로운 benchmark 를 구축한다.

이 unified MCP-based tool suite 는 realistic scenario simulation 과 real-world agent performance evaluation 을 위한 standardized environment 를 제공한다.

또한 MCP 를 지원하는 한 향후 agent framework 또는 product 에도 적용할 수 있으므로 reusable 하고 extensible 한 real-world agent security research testbed 가 된다.

Real-World Agents​

저자는 두 popular agent development framework 인 LangChain 및 OpenAI Agents SDK 와 agent product 인 OpenHands 에 Progent 를 적용한다.

Sec. 7 에서 설명한 대로 Progent 는 서로 다른 user role 을 위해 두 integration mode 를 제공한다.

  • Library mode

    • agent developer 를 위한 mode 이다.

  • Proxy mode

    • end user 를 위한 mode 이다.

LangChain 과 OpenAI Agents SDK 에서는 developer 가 기존 agent 에 최소한의 code modification 으로 Progent 를 추가하는 상황을 simulate 하기 위해 library mode 를 사용한다.

  • LangChain 에서는 developer 가 LangChain SDK 로 agent 를 정의할 때 쉽게 추가할 수 있는 Middleware component 를 구현한다.
  • OpenAI Agents SDK 에서는 Agent class 를 감싸는 wrapper 를 제공하여 Progent functionality 를 seamless 하게 integrate 할 수 있다.

OpenHands 에서는 end user 가 agent 내부 implementation 을 변경하지 않고 transparently Progent 를 사용할 수 있는 proxy mode 를 사용한다.

  • end user 는 agent code 를 modify 할 필요가 없다.
  • LLM 및 MCP server endpoint 를 Progent proxy 로 변경하기만 하면 existing agent product 에 protection 을 적용할 수 있다.

Fig. 8 의 결과는 다음과 같다.

  • Progent 는 real-world agent 전반에서 ASR 를 일관되게 약 1% 수준으로 감소시킨다.
  • 동시에 strong utility 를 유지한다.
  • 서로 다른 agent 사이의 marginal utility 및 security variation 은 system prompt 와 retry mechanism 차이 때문일 가능성이 높다.
  • 결과는 realistic attack scenario 에서 real-world agent 와 함께 deploy 되었을 때 Progent 의 effectiveness 와 robustness 를 보여준다.

Multi-Agent Systems​

Progent 의 modular design 은 multi-agent system 을 자연스럽게 지원한다.

저자는 multi-agent setting 에서 두 가지 integration 방법을 제시한다.

  • Unified integration

    • entire multi-agent system 을 하나의 unified entity 로 취급한다.
    • multi-agent system, environment, LLM 사이의 interface 에 single layer privilege control 을 enforce 한다.
    • global context 및 policy management 를 통해 consistent security 를 제공하고 cross-agent privilege escalation 을 방지한다.

  • Per-agent integration

    • 각 sub-agent 에 Progent 를 별도로 적용한다.
    • 각 agent 의 role 과 functionality 에 맞춘 customized policy 를 사용할 수 있다.
    • 서로 다른 agent 가 distinct user 에 의해 operate 되거나 permission level 차이가 큰 경우 특히 유용하며 isolated privilege control 을 제공한다.

저자의 MCP-based benchmark 에서는 AutoGen 을 사용해 one coordinator 와 6 개의 expert sub-agent 로 구성된 multi-agent system 을 구축한다.

  • general agent

    • user profile 과 password 관리

  • workspace agent

    • calendar, email, file operation 담당

  • slack agent

    • team communication 과 channel management 담당

  • banking agent

    • banking 및 payment-related task 수행

  • travel agent

    • booking 및 itinerary 관리

  • web agent

    • web browsing 과 content posting 담당

모든 sub-agent 가 동일한 user 를 대신해 동작하므로 저자는 unified control 이 더 적합하다고 판단하여 첫 번째 integration 방법을 사용한다.

Fig. 8 의 multi-agent 결과는 다음과 같다.

  • multi-agent setting 에서는 utility 와 ASR 모두 single-agent system 보다 약간 낮다.

  • 이는 multi-agent system 이 sub-agent 사이에 natural isolation 을 도입하기 때문일 가능성이 높다.

    • isolation 은 coordination efficiency 를 감소시킬 수 있다.
    • 동시에 attack propagation 을 제한하여 security 를 향상시킬 수 있다.

  • Progent 적용 후 비슷한 utility 를 유지하면서 security 를 크게 향상시킨다.

  • successful attack 의 95% 이상을 방어한다.

9 Limitation and Discussion

User Mistakes​

Progent 는 deterministic SMT-based checking 을 포함하지만 user mistake 는 여전히 security guarantee 를 위협할 수 있다.

user 가 widening update 를 잘못 approve 하거나 ambiguous initial task 를 제공하면 Progent 는 minimal privilege 를 넘어서는 policy 를 permit 할 수 있다.

policy update mechanism, invariant constraint enforcement, potentially unsafe change 에 대한 explicit approval 요구는 이러한 risk 를 mitigate 하지만 완전히 제거하지는 못한다.

저자는 Appendix E 에서 adaptive attack 을 사용하여 user-introduced mistake 상황의 Progent 를 empirically 평가하며, possible human misjudgment 에도 불구하고 Progent 가 ASR 를 크게 감소시키고 meaningful protection 을 유지함을 보여준다.

Defense Scope​

Progent 는 invariant boundary 밖에 있는 malicious tool call 로부터 agent 를 보호하는 데 초점을 맞춘다. 따라서 dangerous tool call 을 trigger 하지 않고 agent 의 textual output 만 influence 하는 attack 은 다루지 않는다.

이러한 text-to-text attack 은 기존 model security 연구에서 광범위하게 다뤄진 model-level risk 에 더 가깝다.

agent 측면에서 Progent 는 minimal code change 로 다른 defense 를 complement 하는 effective defense-in-depth layer 역할을 한다.

developer 가 agent 에 additional component 를 inject 하기로 선택한다면 다음과 같은 enhanced policy 가 data flow 를 추가로 control 하고 attack 을 mitigate 할 수 있다.

  • potentially malicious data 를 읽는 tool 을 restrict 하는 policy
  • harmful content 를 제거하기 위해 tool output 을 filter 하는 component

또한 proxy mode 는 out-of-the-box deployability 를 제공하고 underlying agent modification 을 요구하지 않지만, external MCP interface 를 우회하는 built-in tool 로 구현된 agent functionality 는 보호할 수 없다.

반면 library mode 는 몇 줄의 code change 만 필요하면서 built-in tool 역시 보호할 수 있다.

따라서 deployability 와 protection depth 사이에 trade-off 가 존재한다.

Extension to Multimodal Agents​

현재 scope 에서 agent 는 text 만 처리할 수 있다. 따라서 저자의 method 는 graphic interface 같은 multimodal element 가 관련된 tool 을 호출하는 agent 에 직접 적용할 수 없다.

예를 들어 다음과 같은 agent action 이 해당한다.

  • browser 의 특정 위치를 click
  • computer screen 의 특정 icon 을 click

향후 흥미로운 연구 방향은 image 와 같은 다른 modality 를 capture 하는 policy 를 설계하는 것이다.

예를 들어 policy 는 agent 가 computer 의 특정 application 만 click 하도록 constrain 할 수 있다. 이를 computer screen 상의 특정 region 으로 transform 하여 agent 가 selected region 에서만 click 하도록 제한할 수 있다.

10 Related Work

Security Policy Languages​

security principle 을 enforce 하는 것은 어렵지만, 기존 연구는 programming 이 viable solution 임을 보여준다.

  • Binder 는 distributed system 에서 authorization 과 delegation 을 위해 Datalog-style inference 를 사용한다.
  • Sapper 는 timing-sensitive noninterference 를 위해 hardware-level check 를 도입한다.
  • cloud 및 application level 에서는 Cedar 가 fine-grained authorization policy 를 표현하기 위한 domain-specific language 를 제공한다.
  • AWS, Microsoft Azure, Google Cloud 와 같은 major cloud platform 역시 established authorization policy language 를 제공한다.

이러한 approach 는 programmatic policy enforcement 가 다양한 security domain 에서 성숙해왔음을 보여준다. 그러나 existing policy language 는 AI agent 의 dynamic behavior 에 적합하지 않다.

이 gap 은 Progent 와 같은 agent-oriented policy 로 자연스럽게 이어진다.

System-Level Defenses for Agents​

agentic task solving 을 위한 system-level defense 는 emerging research field 이다.

  • IsolateGPT 는 application 사이 execution 을 isolate 하고 cross-app communication 또는 irreversible action 과 같이 potentially dangerous 한 operation 에 대해 user confirmation 을 요구하는 agent architecture 를 제안한다.
  • f-secure 는 agent execution 동안 propagate 되는 manually assigned trust label 을 통해 information-flow control 을 enforce 한다.
  • AirgapAgent 는 private data 에 대한 access control 에 초점을 맞춰 agent 가 task-relevant information 만 사용하도록 하지만 data access 를 넘어선 malicious agent behavior 는 control 하지 않는다.
  • CaMeL 은 trusted user query 로부터 control flow 와 data flow 를 extract 하여 untrusted data 가 program flow 에 영향을 주지 못하도록 하지만 agent 내부 architecture 를 modify 해야 하며 utility 에 영향을 준다.
  • FIDES 는 confidentiality 및 integrity label 을 사용하는 dynamic taint tracking 을 통해 agent operation 의 data flow 를 regulate 하지만 data source 에 대한 up-front label assignment 가 필요하다.
  • Conseca 와 DRIFT 역시 agent 를 위한 policy generation 을 제안하지만, 둘 다 policy generation 에 LLM 을 사용하고 deterministic verification 을 제공하지 않는다.

Progent policy 는 SMT-based expansion check 를 지원하도록 structured 되어 있으며, 각 update 를 deterministic 하게 expansion 또는 narrowing 으로 classify 한다.

Progent 에서는 LLM-generated policy update 가 adversarial input 에 의해 manipulate 되더라도 expansion check 가 silent privilege escalation 을 방지한다. 따라서 Conseca 나 DRIFT 가 제공할 수 없는 monotonic confinement guarantee 를 제공한다.

Progent 의 privilege-control approach 는 이러한 defense 를 complement 한다. modular design 으로 existing agent implementation 에 minimal change 만으로 integrate 할 수 있어 adoption barrier 를 낮출 수 있는 반면, 여러 다른 system-level defense 는 상당한 architectural modification 을 요구한다.

Model-Level Prompt Injection Defenses​

parallel research line 은 model level 에서 prompt injection 을 해결하는 데 초점을 맞추며 크게 두 category 로 나눌 수 있다.

  • Guardrail model 기반 defense

    • injected content 를 detect 하도록 guardrail model 을 train 하고 deploy 한다.
    • Fig. 3 의 결과에서 Progent 는 state-of-the-art guardrail method 를 empirically outperform 한다.
    • 또 다른 중요한 차이는 Progent 가 deterministic security enforcement 를 제공하는 반면 guardrail model 은 이를 제공할 수 없다는 것이다.

  • Agent LLM fine-tuning 기반 defense

    • agent LLM 이 prompt injection 에 더 resistant 하도록 fine-tuning 한다.
    • 이러한 defense 는 Progent 의 system-level privilege control 과 다른 level 에서 동작한다.

따라서 Progent 는 model-level defense 와 synergistically 동작할 수 있다. model defense 는 agent 의 core reasoning 을 보호하고, Progent 는 agent 와 external tool 사이의 execution boundary 를 보호한다.

Fig. 7 에서 보이듯 Progent 와 model-level defense 를 결합하면 더 강한 protection 을 제공할 수 있다.

11 Conclusion

저자는 tool-call level 의 privilege control 을 통해 AI agent 를 보호하는 framework 인 Progent 를 제안한다.

Progent 는 tool name 과 argument 에 대한 symbolic rule 로 구성된 privilege control policy 를 도입하며, decision loop 에 LLM 을 사용하지 않고 deterministic 하게 enforce 한다.

다양한 task 와 evolving execution context 를 처리하기 위해 LLM 이 policy 를 자동으로 generate 및 update 하며, deterministic SMT-based check 가 각 update 를 narrowing 또는 expansion 으로 판정한다.

  • narrowing 은 자동으로 적용된다.
  • expansion 은 approval 을 요구한다.

이를 통해 monotonic confinement 를 guarantee 한다.

AgentDojo 와 ASB 에 대한 evaluation 은 Progent 가 높은 utility 를 유지하면서 attack success rate 를 크게 감소시킨다는 것을 보여준다. 또한 LangChain 과 OpenAI Agents SDK 와 같은 real-world agent framework 와의 integration 을 통해 Progent 가 non-intrusive defense-in-depth layer 로서 practical 하다는 것을 확인한다.
